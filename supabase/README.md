# Подключение Supabase

Без переменных окружения игра работает локально. Сообщение «Прогресс сохранён локально» означает localStorage этого браузера. Облачное сохранение требует настройки ниже.

1. На [supabase.com](https://supabase.com/) создайте Project в своём аккаунте. Сохраните пароль базы вне проекта.
2. Откройте **SQL Editor → New query**, вставьте весь `supabase/setup.sql` и нажмите **Run**. Альтернатива: выполните сначала `schema.sql`, затем `policies.sql`. Это одинаковые варианты установки, выполнять оба не нужно. Скрипты можно повторить на созданной ими схеме. Полный setup.sql также обновляет старое ограничение подсказок до шести, сохраняя попытки и рекорды.
3. Откройте **Authentication → Sign In / Providers** (в некоторых версиях панели **Providers**) и включите **Anonymous Sign-Ins**. Игра вызывает `signInAnonymously()`; email не нужен. Анонимный вошедший пользователь использует PostgreSQL-роль `authenticated`.
4. В **Project Settings → Data API** скопируйте **Project URL**. В **Settings → API Keys** возьмите **publishable key** вида `sb_publishable_…`. Никогда не используйте `sb_secret_…` и `service_role` в браузере.
5. В корне игры скопируйте `.env.example` в `.env`:

   ```dotenv
   VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
   ```

6. Перезапустите `npm run dev`. На Vercel задайте эти две переменные в **Settings → Environment Variables** и выполните новый deploy: Vite подставляет переменные при сборке.
7. Введите ник и завершите первый уровень. Дождитесь сообщения **«Прогресс сохранён в облаке»**. При ошибке авторизации проверьте Anonymous Sign-Ins, URL и ключ; при ошибке таблиц или прав — выполнение setup.sql. При временной сетевой ошибке игра продолжает сохранять результаты локально и повторяет синхронизацию после восстановления подключения.
8. В Supabase **Authentication → Users** найдите нового анонимного пользователя. В **Table Editor → profiles** должна появиться его строка с ником. В `runs` — попытка, в `level_progress` — рекорд уровня. Повторное прохождение создаёт другую попытку; повторная отправка одной попытки не создаёт дубликат, потому что её UUID неизменен.
9. Обновите страницу: ник, доступные уровни и рекорды должны восстановиться. Откройте статистику и сравните её с `level_progress` / `runs`. Время, ошибки и звёзды хранятся как независимые лучшие значения; они могут относиться к разным попыткам. В каждом уровне теперь три терминала и до шести подсказок (по две на задачу).

## Обновление установленной базы до трёх терминалов

Если исходная игра уже подключена к Supabase, выполните **supabase/upgrade-three-puzzles.sql** целиком в SQL Editor. Скрипт расширит CHECK `runs_hints_used_check` с диапазона 0–2 до 0–6 и затем покажет действующее ограничение. Повторное выполнение безопасно. Удалять таблицы, пользователей, историю и рекорды не требуется. Альтернатива — повторно выполнить весь обновлённый setup.sql: он содержит такое же расширение и восстанавливает заявленные RLS-политики.

Простого изменения CREATE TABLE IF NOT EXISTS недостаточно: существующий CHECK остаётся прежним. При старом ограничении игра сохранит попытку с 3–6 подсказками локально и покажет сообщение о необходимости обновления SQL; после обновления кнопка повторной синхронизации отправит тот же UUID без дубликатов.

Награды не менялись: три звезды — ноль ошибок и ноль подсказок; две — не более двух ошибок и одной подсказки; иначе одна. Звёзды считаются за весь уровень, а не отдельно за каждый терминал. Предыдущие результаты и открытые уровни сохраняются.

## Настройки Data API и анонимного входа

В актуальных проектах Supabase доступ к созданным SQL-таблицам может требовать явных GRANT. В setup.sql они уже есть: `authenticated` получает SELECT/INSERT/UPDATE на свои профили и прогресс, SELECT/INSERT на свою историю, а роль `anon` не получает доступ к этим таблицам. Убедитесь, что схема `public` доступна через Data API; право на таблицу и RLS выполняют разные задачи.

Supabase рекомендует CAPTCHA или Cloudflare Turnstile для открытого анонимного входа и применяет ограничение числа регистраций с одного IP (по текущей документации по умолчанию 30 в час). Сейчас игра восстанавливает существующую сессию и не создаёт новую для каждого уровня. Если включить обязательную CAPTCHA в Dashboard, для новой регистрации также потребуется добавить виджет и передавать его `captchaToken` в signInAnonymously; одно переключение настройки без виджета сделает новые входы недоступными. Для закрытого тестового проекта можно оставить CAPTCHA выключенной. При запросе CAPTCHA или лимите регистраций игра сообщает причину и продолжает сохранять результаты локально.

Документация: [Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous), [CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [защита Data API](https://supabase.com/docs/guides/api/securing-your-api).

## Проверка изоляции пользователей

Проверяйте через два профиля браузера или обычное и приватное окно. Две вкладки одного профиля используют одну анонимную сессию и для этой проверки не подходят.

1. В профиле A создайте ник и пройдите уровень. Запишите UUID A из `Authentication → Users` или `profiles`.
2. В профиле B создайте другой ник. В B не должны появиться данные A. Запишите UUID B. Оба пользователя должны реально существовать в `auth.users`.
3. В SQL Editor выполните следующий блок, заменив UUID. `SET LOCAL ROLE` обязателен: обычный SQL Editor работает с административными правами и сам по себе не проверяет RLS.

   ```sql
   begin;
   set local role authenticated;
   select set_config('request.jwt.claim.sub', 'UUID_ПОЛЬЗОВАТЕЛЯ_B', true);
   select auth.uid(); -- должен показать B
   select * from public.profiles where id = 'UUID_ПОЛЬЗОВАТЕЛЯ_A';
   select * from public.level_progress where user_id = 'UUID_ПОЛЬЗОВАТЕЛЯ_A';
   select * from public.runs where user_id = 'UUID_ПОЛЬЗОВАТЕЛЯ_A';
   update public.profiles set nickname = 'ЧужойНик'
     where id = 'UUID_ПОЛЬЗОВАТЕЛЯ_A' returning *;
   rollback;
   ```

   Все три выборки должны быть пустыми; UPDATE возвращает ноль строк. ROLLBACK отменяет любые изменения проверки.

4. В отдельной транзакции с той же ролью B проверьте чужую запись:

   ```sql
   begin;
   set local role authenticated;
   select set_config('request.jwt.claim.sub', 'UUID_ПОЛЬЗОВАТЕЛЯ_B', true);
   insert into public.runs(user_id, level_id, duration_ms, mistakes, hints_used)
     values ('UUID_ПОЛЬЗОВАТЕЛЯ_A', 1, 1000, 0, 0);
   rollback;
   ```

   INSERT должен завершиться ошибкой нарушения RLS. Если редактор остановил выполнение на ошибке, отдельно выполните `rollback;`.

5. UPDATE и DELETE таблицы `runs` от роли `authenticated` должны давать `permission denied`: история доступна для чтения и добавления собственных строк. Клиент использует `INSERT … ON CONFLICT DO NOTHING`, сохраняя один UUID попытки при повторе.

## Важные ограничения

- Очистка данных браузера может удалить анонимную сессию. Без полноценной учётной записи нельзя обещать перенос между устройствами или восстановление доступа. Несинхронизированные результаты старого владельца не отправляются под новым пользователем.
- RLS защищает данные одного пользователя от другого. Клиентское прохождение не является защитой от читерства: для соревновательного рейтинга нужна серверная проверка.
- Скрипт предназначен для новой схемы игры; он не удаляет неизвестные политики, которые были добавлены вручную. Для аудита проверьте `pg_policies` и выдаваемые права в существующем проекте.
- Интеграционные запросы и политики необходимо проверить на вашем Supabase-проекте после настройки. Наличие SQL и модульных тестов не означает, что облачное подключение уже было проверено.
