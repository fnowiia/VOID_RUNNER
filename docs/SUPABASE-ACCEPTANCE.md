# Приёмка реального сохранения Supabase

Эта проверка выполняется в вашем тестовом Supabase после применения `supabase/setup.sql` и настройки переменных. Локальные модульные тесты не заменяют проверку анонимной авторизации, серверных прав и RLS.

## Подготовка

1. Используйте отдельный тестовый проект без ценных данных.
2. Выполните `setup.sql` целиком, включите Anonymous Sign-Ins и задайте URL/publishable key.
3. Запустите игру через HTTP. Для проверки production используйте `npm run build`, затем `npm run preview`.
4. Откройте игру в обычном окне браузера — это пользователь **A**.
5. Откройте игру в отдельном приватном окне или другом браузерном профиле — это пользователь **B**. Две обычные вкладки одного сайта разделяют сессию и не являются двумя пользователями.
6. Укажите различающиеся ники. В Supabase Authentication → Users запишите UUID обоих пользователей. Для явной проверки RLS используйте клиент с публичным ключом и сессией конкретного пользователя. SQL Editor работает с административными правами и не доказывает изоляцию браузерных сессий.

## Сохранение и восстановление

- [ ] Пользователь A появился в `auth.users`, профиль A содержит его ник.
- [ ] Пользователь B получил другой UUID и отдельный профиль.
- [ ] После прохождения A в `runs` появилась одна запись с его `user_id` и `level_id`.
- [ ] Сектор считается завершённым после всех трёх терминалов; незавершённая попытка после монстра не записана как успешное прохождение.
- [ ] В `level_progress` появилась строка A для этого уровня с положительным временем и звёздами 1–3.
- [ ] Интерфейс показал облачное сохранение только после успешного завершения запросов.
- [ ] После обновления A сохранились ник, статистика и открытый следующий уровень.
- [ ] B не получил прогресс и разблокировки A.
- [ ] Повторное худшее прохождение A добавило запись истории, но не ухудшило лучшие показатели.
- [ ] Изменение ника A обновило только его профиль.
- [ ] Завершение сектора с 3–6 подсказками успешно синхронизируется: в `runs.hints_used` допустим диапазон 0–6.
- [ ] Полный перезапуск текущего сектора после монстра не удалил ранее завершённые уровни, историю и рекорды из базы.

## Отключение сети и повторная отправка

1. В браузере A включите Offline в Network DevTools или временно отключите сеть.
2. Завершите уровень. Проверьте статус локального сохранения, восстановление после обновления и отсутствие ложного облачного подтверждения.
3. Включите сеть. Дождитесь синхронизации или повторно откройте игру при доступной сети.
4. Сверьте UUID попытки в `runs`: она должна существовать один раз. Повторное обновление страницы и синхронизация не должны создавать дубликаты той же попытки.
5. Убедитесь, что успешная синхронизация очистила очередь ожидающих результатов и сохранила лучшие показатели.
6. В отдельном тестовом профиле проверьте утрату сессии. Результаты, уже привязанные к UUID A, не должны отправляться от имени нового пользователя B.

## Проверка RLS

Выполняйте запросы от имени A через Supabase JS SDK, REST или приложение с его действующим access token. Используйте публичный ключ и фактические UUID. Не используйте `service_role` или SQL Editor для этой части.

| Проверка от имени A | Ожидаемый результат |
| --- | --- |
| SELECT `profiles` без фильтра | Только профиль A |
| SELECT `level_progress` без фильтра | Только строки A |
| SELECT `runs` без фильтра | Только история A |
| INSERT собственного профиля | Разрешён при соблюдении ограничений и отсутствии дубликата |
| UPDATE собственного ника | Разрешён; длина 2–16 символов |
| INSERT прогресса с `user_id` A | Разрешён при допустимых значениях |
| UPDATE собственного прогресса | Разрешён; лучшие показатели не ухудшаются |
| INSERT попытки с `user_id` A | Разрешён при допустимых значениях |
| SELECT по UUID B | Пустой набор строк |
| INSERT профиля с `id` B | Отклонён RLS либо конфликтом существующего ключа |
| INSERT прогресса с `user_id` B | Отклонён RLS |
| INSERT попытки с `user_id` B | Отклонён RLS |
| UPDATE профиля или прогресса B | Ни одна чужая строка не изменена |
| UPDATE или DELETE истории `runs` | Отклонён отсутствующими правами; история доступна только для добавления и чтения |
| DELETE чужих или собственных персональных строк из клиента | Отклонён отсутствующими правами |

При UPDATE чужого UUID PostgREST может вернуть успешный HTTP-статус и **ноль изменённых строк**: RLS скрывает чужую строку. Проверяйте фактическое число изменённых записей и данные B после операции, а не только код HTTP.

Дополнительно проверьте ограничения: недопустимые `level_id`, звёзды вне 1–3, отрицательные ошибки/подсказки/время, подсказки выше 6, ник длиной 1 или 17 символов должны отклоняться. Сессия без анонимного входа не должна получать персональные записи. Для базы старой версии предварительно выполните `supabase/upgrade-three-puzzles.sql` либо обновлённый `setup.sql`: старый CHECK 0–2 иначе отклонит завершённую попытку с 3–6 подсказками.

Сохраните фактический результат каждой проверки, версии SQL и дату. Для состязательного рейтинга эти проверки недостаточны: клиент может подставлять игровые результаты, поэтому нужна отдельная серверная валидация.
